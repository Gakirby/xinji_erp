# 数据库设计

- 数据库：`xinji_erp`
- 引擎：InnoDB / 字符集 `utf8mb4` / 排序 `utf8mb4_general_ci`
- 建表脚本：`server/src/main/resources/db/schema.sql`
- 演示数据：`server/src/main/resources/db/data.sql`
- 表名前缀统一 `t_`（MyBatis-Plus 配了 `table-prefix: t_`，实体类不写前缀）

共 **21 张表**，按业务域分七组：

| 分组 | 表 |
| --- | --- |
| 主数据 | `t_customer`、`t_user`、`t_warehouse`、`t_sku` |
| 交易 | `t_order`、`t_order_item`、`t_weigh_ticket` |
| 库存 | `t_stock_flow` |
| 秒杀 | `t_seckill_activity`、`t_seckill_sku`、`t_seckill_token` |
| 财务 | `t_settlement`、`t_settlement_item`、`t_receivable`、`t_purchase_order` |
| 调度 | `t_vehicle`、`t_driver`、`t_dispatch` |
| 生产 / 票据 | `t_production_order`、`t_payment`、`t_invoice` |

## 一、设计主线：库存双池

这是整套系统最核心的一个设计决定，先说清楚再看表。

一块矿石从进矿到出矿，要经过「采购入库 → 划一部分去做活动 → 客户下单锁货 → 装车过磅 → 出厂」。如果只有一个 `stock` 字段，销售和活动会互相抢货：活动报了 800 吨，销售就只剩能卖 800 吨，两边都算不清。

所以在 `t_sku` 上放了三个数：

```
物理总库存 = stock_qty（销售可售） + activity_alloc_qty（活动划拨） + frozen_qty（订单冻结）
```

| 动作 | stock_qty | activity_alloc_qty | frozen_qty | 物理总量 |
| --- | --- | --- | --- | --- |
| 采购入库 120 吨 | +120 | — | — | **+120** |
| 划拨 100 吨做活动 | −100 | +100 | — | 不变 |
| 客户下单 30 吨 | −30 | — | +30 | 不变 |
| 出厂核销 | — | — | −30 | **−30** |
| 秒杀成交 20 吨 | — | −20 | — | **−20** |
| 活动剩余回拨 | +50 | −50 | — | 不变 |
| 取消订单 | +30 | — | −30 | 不变 |

好处：

1. **两个池子永远加得起来** —— 随时能验证「三个数之和等于实际库存」，对不上一眼就看出来
2. **活动不会占用销售的货** —— 客户在商城看到的是 `stock_qty`，不会把活动预留的量算进去
3. **冻结量单独记账** —— 已下单未发货的货既不能卖也不能算库存，单独一列最清楚

每发生一次变动，都往 `t_stock_flow` 写一条带 `before_qty / after_qty` 的流水。出了纠纷可以逐笔倒推。

## 二、主数据

### 2.1 t_customer 客户档案

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | 主键 |
| customer_no | VARCHAR(32) UK | 客户编号 `C-1001` |
| customer_name | VARCHAR(120) | 客户名称 |
| contact_name / contact_phone | VARCHAR | 联系人、电话 |
| address | VARCHAR(200) | 默认收货地址 |
| credit_limit | DECIMAL(14,2) | 授信额度（元） |
| credit_used | DECIMAL(14,2) | 已用额度（元） |
| status | TINYINT | 1 正常 / 0 停用 |

**设计取舍**：授信额度做成「已用额度」的累加字段，下单时校验 `credit_used + pay_amount <= credit_limit`，下单加、取消减、回款减。
没有做成实时汇总视图，是因为下单要快，加一次汇总查询在高峰期是明显的开销。

### 2.2 t_user 登录账号

客户和员工**共用一张表**，用 `user_type` 区分。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| username | VARCHAR(40) UK | 登录名 |
| password | VARCHAR(100) | BCrypt 哈希 |
| mobile | VARCHAR(20) | 手机号（小程序授权登录可复用） |
| user_type | VARCHAR(16) | `CUSTOMER` / `EMPLOYEE` |
| customer_id | BIGINT | 客户账号绑定的客户 ID（员工为 NULL） |
| employee_name | VARCHAR(40) | 员工姓名 |
| role | VARCHAR(24) | `ADMIN/SALES/FINANCE/WEIGH/DISPATCH/CUSTOMER` |
| status | TINYINT | 1 启用 / 0 禁用 |

**为什么客户和员工放一张表**：登录逻辑完全一样（账号+密码+性格角色），分成两张表要写两套登录、两套 JWT 签发。用 `user_type` 一个字段区分就够了，`AuthInterceptor` 再按 `user_type` 拦接口。

**一个客户多个账号**是支持的（比如采购员 A、采购员 B 都能登），它们的 `customer_id` 相同，看到的订单是同一份 —— 这也是网页商城和小程序能无缝切换的原因。

### 2.3 t_warehouse 料仓

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| warehouse_no | VARCHAR(20) UK | `A1` / `A2` / `B1` / `B2` / `C1` |
| warehouse_name | VARCHAR(60) | 料仓名称 |
| capacity | DECIMAL(14,3) | 设计容量（吨） |

一个物料挂一个主料仓；石粉和尾矿共用一个堆场 `C1`，所以 `warehouse_id` 不是唯一的，只在 `t_sku` 上做普通索引。

### 2.4 t_sku 物料 SKU（双池核心表）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| sku_no | VARCHAR(32) UK | `SKU-1001` |
| sku_name | VARCHAR(80) | 物料名称 |
| category | VARCHAR(30) | 石灰石 / 机制砂 / 铁精粉 / 石粉 / 尾矿 |
| spec | VARCHAR(60) | 规格描述 |
| unit | VARCHAR(10) | 单位，默认「吨」 |
| price | DECIMAL(12,2) | 挂牌价（元/吨） |
| warehouse_id | BIGINT | 主料仓 |
| **stock_qty** | DECIMAL(14,3) | **销售可售量** —— 客户下单扣这个 |
| **activity_alloc_qty** | DECIMAL(14,3) | **活动池划拨量** —— 从可售池切出去的量 |
| **frozen_qty** | DECIMAL(14,3) | **订单冻结量** —— 已下单未出厂 |
| safety_qty | DECIMAL(14,3) | 安全库存线，低于它前端标「偏低 / 紧张」 |
| image_tag | VARCHAR(20) | 前端占位色标（原型用，正式版换成图片 URL） |
| status | TINYINT | 1 在售 / 0 下架 |

**为什么用 DECIMAL(14,3)**：吨是小数，过磅精度到 0.001 吨（1 公斤）。用 DOUBLE 会有精度漂移，结算金额对不上账，必须用定点数。

**条件更新的写法**（防超卖的关键）：

```sql
UPDATE t_sku SET stock_qty = stock_qty - #{qty}, frozen_qty = frozen_qty + #{qty}
WHERE id = #{id} AND stock_qty >= #{qty}
```

`AND stock_qty >= #{qty}` 是最后一道防线：并发时数据库行锁保证只有一个线程能更新成功，返回影响行数 0 就说明库存不够。业务层不需要额外加锁。

## 三、交易

### 3.1 t_order 订单

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| order_no | VARCHAR(32) UK | 订单号 `XJ202611010001948` |
| customer_id | BIGINT | 客户 ID |
| customer_name | VARCHAR(120) | 客户名称**冗余** |
| order_type | VARCHAR(16) | `NORMAL` 常规 / `SECKILL` 抢购 |
| status | VARCHAR(24) | 见下方状态机 |
| total_qty | DECIMAL(14,3) | 下单吨数 |
| total_amount | DECIMAL(14,2) | 商品金额 |
| freight | DECIMAL(12,2) | 运费 |
| discount_amount | DECIMAL(12,2) | 优惠金额 |
| pay_amount | DECIMAL(14,2) | 应付金额 |
| delivery_type | VARCHAR(16) | `DELIVERY` 配送 / `PICKUP` 自提 |
| expected_date | VARCHAR(40) | 期望到货时段（字符串，如「11-05 08:00 — 12:00」） |
| address / receiver | VARCHAR | 卸货地址、收货人（下单时快照） |
| seckill_token | VARCHAR(40) | 抢购令牌号（常规单为 NULL） |
| remark | VARCHAR(200) | 备注 |

**订单状态机**

```
PENDING_AUDIT（待审核）
   ├─ audit ──→ AUDITED（已审核）
   │              ├─ dispatch ──→ DISPATCHED（已派车）
   │              │                  └─ ship ──→ SHIPPED（已出厂）
   │              │                                └─ sign ──→ SIGNED（已签收）
   │              │                                              └─ 生成对账批次 → SETTLED（已对账）
   │              │                                                                └─ 开票 → INVOICED
   │              │                                                                            └─ 回款 → PAID
   └─ cancel ──→ CANCELLED（已取消）
```

`OrderStatus.canTransfer(from, to)` 用一个枚举白名单控制合法流转，非法流转直接被拒：
「订单当前状态为「已出厂」，不能流转到「已审核」」。

**customer_name / address / receiver 为什么冗余**：客户改名或改地址后，历史订单要显示当时的名称和地址，不能跟着变。这是订单类表的标准做法。

**expected_date 为什么是字符串**：矿石配送的时段是人话（「11-05 08:00 — 12:00」「11-03 全天」），不是精确时间点；用两个 DATETIME 反而表达不了「全天」这种区间。

### 3.2 t_order_item 订单明细

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| order_id / order_no | BIGINT / VARCHAR | 关联订单 |
| sku_id / sku_name / spec | | 物料信息**快照** |
| qty | DECIMAL(14,3) | 下单吨数 |
| price | DECIMAL(12,2) | 成交单价（可能是活动价） |
| amount | DECIMAL(14,2) | 小计 |
| **settle_qty** | DECIMAL(14,3) | **结算吨数** —— 过磅后回填 |
| **settle_amount** | DECIMAL(14,2) | **结算金额** —— 过磅后回填 |

**settle_qty 是这张表最重要的字段**。客户下单 120 吨，实际过磅扣水扣杂后只有 95.12 吨，财务必须按 95.12 收钱。
回填时机是过磅出票，之后不再变动 —— 先把数定死，避免月底对账时双方各算一遍各说各话。

`price` 也要快照：活动价 72 和挂牌价 86 是两回事，物料调价后历史订单金额不能变。

### 3.3 t_weigh_ticket 地磅单

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| ticket_no | VARCHAR(32) UK | 磅单号 `BD202611010001937` |
| order_no | VARCHAR(32) | 关联订单 |
| sku_id | BIGINT | 物料 |
| plate_no | VARCHAR(20) | 车牌 |
| driver_name / driver_phone | VARCHAR | 司机信息 |
| gross_weight | DECIMAL(12,3) | 毛重（重车） |
| tare_weight | DECIMAL(12,3) | 皮重（空车） |
| net_weight | DECIMAL(12,3) | 净重 = 毛重 − 皮重 |
| water_rate | DECIMAL(6,4) | 含水率（0.011 = 1.1%） |
| water_deduct_weight | DECIMAL(12,3) | 扣水量 = 净重 × 含水率 |
| impurity_deduct_weight | DECIMAL(12,3) | 扣杂量（人工填） |
| settle_weight | DECIMAL(12,3) | 结算吨数 = 净重 − 扣水 − 扣杂 |
| weigh_time / weighman | | 过磅时间、磅员 |
| status | VARCHAR(16) | `ISSUED` 已出票 / `VOID` 作废 |

**四个重量字段全存**，不只存结算量。客户质疑扣多的时候，把毛重皮重含水率摊开给他看，比一句「系统算的」有说服力得多。

一张订单可以有多张磅单（一车一单），`t_order_item.settle_qty` 是这些磅单结算量的累加。

## 四、库存

### 4.1 t_stock_flow 库存流水

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| flow_no | VARCHAR(32) | 流水号 `LS202611010003794` |
| sku_id / warehouse_id | BIGINT | 物料、料仓 |
| biz_type | VARCHAR(20) | 见下表 |
| qty | DECIMAL(14,3) | 变动量（正负） |
| before_qty / after_qty | DECIMAL(14,3) | 变动前后的**可售量** |
| biz_no | VARCHAR(32) | 关联单号（订单号 / 采购单号 / 活动号） |
| remark | VARCHAR(200) | 说明 |
| operator | VARCHAR(40) | 操作人 |
| created_at | DATETIME | 发生时间 |

**业务类型**

| biz_type | 触发点 | 对可售池 | 对物理总量 |
| --- | --- | --- | --- |
| `INBOUND` | 采购到货入库 | +qty | +qty |
| `OUTBOUND` | 订单出厂核销冻结 | 不变 | −qty |
| `FREEZE` | 客户下单 | −qty | 不变 |
| `UNFREEZE` | 取消订单 | +qty | 不变 |
| `ALLOC` | 划拨到活动池 | −qty | 不变 |
| `RETURN` | 活动剩余量回拨 | +qty | 不变 |
| `CHECK` | 盘点调整（预留） | ±qty | ±qty |

索引 `idx_sku_time (sku_id, created_at)` 是为了「查某个物料最近的流水」这个高频场景 —— 库存对不上时第一个动作就是这个查询。

**OUTBOUND 的 before_qty = after_qty 不是 bug**：可售池在下单（FREEZE）时已经扣过了，出厂只是核销冻结量，可售池确实没变。所以流水里 `qty = -30` 表示物理库存减少 30 吨，`before/after` 保持可售池口径不变，备注里写清楚「出厂核销冻结 30 吨，物理库存减少」。

## 五、秒杀

### 5.1 t_seckill_activity 活动

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| activity_no | VARCHAR(32) UK | `ACT-20261101` |
| activity_name | VARCHAR(120) | 活动名称 |
| start_time / end_time | DATETIME | 活动起止 |
| status | VARCHAR(16) | `DRAFT` / `PUBLISHED` / `RUNNING` / `ENDED` |
| warmup_status | VARCHAR(16) | `NONE` / `PENDING` / `DONE` —— 库存是否已装载进 Redis |
| created_by | VARCHAR(40) | 创建人 |

`warmup_status` 是给运维看的：活动开始前发现还是 `NONE`，说明忘了预热，赶紧补。

### 5.2 t_seckill_sku 活动 SKU（活动库存池）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| activity_id | BIGINT | 所属活动 |
| seckill_sku_no | VARCHAR(32) UK | `ASK-10022` |
| sku_id | BIGINT | 对应物料 |
| sku_name | VARCHAR(80) | 物料名快照 |
| seckill_price | DECIMAL(12,2) | 抢购价 |
| original_price | DECIMAL(12,2) | 原价（划线价） |
| **activity_stock** | DECIMAL(14,3) | **活动库存总量**（从 `t_sku.activity_alloc_qty` 划拨而来） |
| **sold_qty** | DECIMAL(14,3) | **已抢吨数** |
| limit_per_user | DECIMAL(14,3) | 每人限购吨数，默认 60 |
| status | VARCHAR(16) | `ON` / `OFF` / `SOLDOUT` |

`activity_stock` 和 `sold_qty` 分开存，不存「剩余量」：剩余 = 总量 − 已抢，永远是算出来的。
这样条件扣减能写成 `WHERE activity_stock - sold_qty >= #{qty}`，天然幂等 —— 重复执行不会多扣。

唯一索引 `uk_activity_sku (activity_id, sku_id)`：同一个活动里一个物料只能有一条活动 SKU。

### 5.3 t_seckill_token 抢购令牌

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| token_no | VARCHAR(40) UK | 令牌号 `TK202611010001126` |
| user_id | BIGINT | 抢购用户 |
| customer_id | BIGINT | 下单客户（发放时补） |
| activity_id / seckill_sku_id / sku_id | BIGINT | 关联信息 |
| qty | DECIMAL(14,3) | 抢到的吨数 |
| price | DECIMAL(12,2) | 活动价快照 |
| status | VARCHAR(16) | `PENDING` 发放中 / `ISSUED` 待核销 / `USED` 已下单 / `EXPIRED` 已过期 / `FAILED` 失败 |
| expire_time | DATETIME | 过期时间（默认 15 分钟后） |
| order_no | VARCHAR(32) | 核销后生成的订单号 |
| fail_reason | VARCHAR(200) | 失败原因 |

**为什么要有令牌这一层**：抢购接口要在毫秒级返回，不可能同步做完「扣库存 + 建订单 + 建明细」。
所以抢到的是「提货资格」，异步落库后再让客户拿令牌下单。好处：

1. 抢购接口只碰 Redis，响应稳定在几毫秒
2. 客户可以慢慢填收货信息，不会因为填表慢了丢单
3. 15 分钟不兑换自动释放，库存不会被无效占用

**唯一索引 `uk_user_sku (user_id, seckill_sku_id)`** 是「一人一单」的数据库兜底。
即使 Redis 的已抢集合被清空、或者消息重复消费，这张表也插不进第二条。

### 6.2 t_settlement_item 对账明细

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| settlement_id | BIGINT | 所属批次 |

没有这个约束，客户月底点两次「生成对账」就会重复收款，是财务系统最不能出的错。

### 6.3 t_receivable 应收账款

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |

收款不允许多收（`received_amount + amount > amount` 直接拒），避免账做花。

### 6.4 t_purchase_order 采购单

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| po_no | VARCHAR(32) UK | `CG202611010001514` |
| supplier_name | VARCHAR(120) | 供应商 |
| sku_id / sku_name | | 采购物料 |
| plan_qty | DECIMAL(14,3) | 计划采购量 |
| arrived_qty | DECIMAL(14,3) | 累计到货量 |
| price | DECIMAL(12,2) | 采购单价 |
| arrived_amount | DECIMAL(14,2) | 到货金额 = 到货量 × 单价 |
| status | VARCHAR(16) | `PENDING` 在途 / `PARTIAL` 部分到货 / `DONE` 已完成 |
| expected_date | DATE | 预计到货日 |

MVP 只做到货入库单向（采购 → 入库），没有做采购退货和供应商结算。
到货时不是直接 `UPDATE t_sku`，而是调 `StockService.inbound` 写台账 —— 保证库存和流水永远成对。

## 七、调度 / 生产 / 票据（扩展域）

这一组表补齐了原来只有「订单—库存—财务」三段的问题：矿石要有车拉、有产线加工、有发票和回款流水。

### 7.1 t_vehicle 车辆档案

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `plate_no` | VARCHAR(20) | 车牌号，唯一索引 |
| `vehicle_type` | VARCHAR(30) | 自卸车 / 半挂牵引 / 罐车 |
| `load_capacity` | DECIMAL(10,3) | 核定载重（吨），派车时校验不能超载 |
| `insurance_expire` | DATE | 保险到期日，过期车辆不允许派车 |
| `status` | TINYINT | 1 可用 / 0 停用 |

### 7.2 t_driver 司机档案

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `driver_name` / `phone` | VARCHAR | 姓名与电话，派车单会冗余一份 |
| `id_card` | VARCHAR(24) | 身份证号（脱敏存储） |
| `license_no` | VARCHAR(32) | 驾驶证号 |

### 7.3 t_dispatch 派车单

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `dispatch_no` | VARCHAR(32) | 派车单号 `PC...`，唯一 |
| `order_no` | VARCHAR(32) | 关联订单，索引 |
| `vehicle_id` / `plate_no` | BIGINT / VARCHAR | 车辆 ID + 车牌冗余，车牌改了历史单也不变 |
| `driver_id` / `driver_name` / `driver_phone` | | 司机信息冗余 |
| `plan_qty` | DECIMAL(14,3) | 计划装载吨数，必须 ≤ 车辆核定载重 |
| `plan_time` | DATETIME | 计划发车时间 |
| `status` | VARCHAR(16) | PENDING / LOADING / SHIPPED / DONE / CANCELLED |

> 唯一性约束放在业务层：同一订单不允许存在第二张「进行中」的派车单（`status not in ('CANCELLED','DONE')`）。
> 派车成功会把订单从 `AUDITED` 推进到 `DISPATCHED`，两边状态永远一致。

### 7.4 t_production_order 生产工单

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `production_no` | VARCHAR(32) | 工单号 `SC...` |
| `line_name` / `shift` | VARCHAR | 产线与班次 |
| `sku_id` / `sku_name` | | 产出物料 |
| `plan_qty` / `output_qty` / `feed_qty` | DECIMAL(14,3) | 计划产量 / 实际产量 / 投料量 |
| `status` | VARCHAR(16) | PENDING / RUNNING / DONE / CANCELLED |
| `start_time` / `end_time` / `operator` | | 开完工时间与班组长 |

> 完工报产调 `StockService.inbound` 入销售可售池，业务单号用 `production_no`，
> 所以台账里能一眼分清「采购入库」和「生产入库」；投料量只记录不动 SKU 库存（原料是毛石堆场）。

### 7.5 t_payment 收款流水

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `payment_no` | VARCHAR(32) | 收款流水号 `SK...` |
| `receivable_id` / `receivable_no` | | 关联应收单 |
| `customer_id` / `customer_name` | | 客户冗余，方便按客户查回款 |
| `amount` | DECIMAL(14,2) | 本次收款金额 |
| `pay_method` | VARCHAR(16) | TRANSFER / CASH / CHECK / DRAFT |
| `pay_time` / `operator` | | 到账时间与经办人 |

> `t_receivable.received_amount` 是余额口径，`t_payment` 是流水口径，两者在同一事务里更新。
> 只累加余额不落流水，客户对账时说不清哪笔钱哪天到的。

### 7.6 t_invoice 发票

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `invoice_no` | VARCHAR(32) | 发票申请号 `FP...` |
| `settlement_id` / `receivable_id` | BIGINT | 挂对账批次或应收单，二选一 |
| `invoice_type` | VARCHAR(16) | VAT_SPECIAL 专票 / VAT_NORMAL 普票 |
| `amount` | DECIMAL(14,2) | 价税合计 |
| `tax_rate` / `tax_amount` | DECIMAL | 税率与税额（税额 = 价税合计 ÷ (1+税率) × 税率） |
| `status` | VARCHAR(16) | PENDING / ISSUED / VOID |

> 开票金额必须来自单据，不允许手工填一个数字另开一张 —— 否则发票金额和结算金额永远对不上。
> 开具成功后，该对账批次下的订单从 `SETTLED` 推进到 `INVOICED`。

## 九、没有做的事（MVP 边界）

诚实说明，避免验收时以为是 bug：

| 项 | 现状 | 后续 |
| --- | --- | --- |
| 采购退货 | 未实现 | 加 `RETURN_PURCHASE` 业务类型 + 负向入库 |
| 供应商结算 | 未实现 | 类似客户应收，做应付表 |
| 发票管理 | 只有订单状态位 `INVOICED` | 加发票表和开票流水 |
| 盘点 | `t_stock_flow` 预留 `CHECK` 类型 | 加盘点单 + 差异调整 |
| 多料仓调拨 | 未实现 | 加调拨单，同时改两边的 `warehouse_id` 库存 |
| 操作审计日志 | 只在流水表记了 operator | 加统一的操作日志表和 AOP 切面 |
| 软删除 | 主数据用 `status` 停用代替 | 需要历史追溯时加 `deleted` 字段 |
| 分库分表 | 单库单表 | 订单表过千万后按 `customer_id` 或时间分片 |

这些不影响当前验收，都是明确的下一期范围。
